**Bug A — display phantom (branch `fix/est-locked-profit-exceeds-pnl`, HEAD 747bcbd8) — SUPERSEDED, see CORRECTION below.** `routes_futures_terminal.py` EST.LOCKED = keep%(75%) of the favourable PEAK with no reality bound → sailed past P&L when the stop never trailed. **CORRECTION (2026-06-22 PM, DEPLOYED main c87d5cd6, dashboard restarted):** the morning clamp tied EST.LOCKED to the protective STOP, but the US-futures ratchet protects via the runner EXIT (profit_ratchet_exit give-back), NOT the stop trailing. A wide native-trail loss-cap then left EST.LOCKED BLANK even on a perfectly-armed WORKING ratchet → operator: "MNQ +profit, ratchet not firing." Fix: `_bounded_locked_profit(peak_floor, *, avg, last, contracts, mult)` (NO stop param) = `min(peak_floor, current_pnl)`, floored at 0 → shows the ratchet-exit floor, capped at P&L (never > mark; None when at a loss). Tests rewritten (armed-and-holding SHOWS the floor; give-back-past-floor caps at P&L; invariant). **The ratchet itself was NEVER broken** — MNQ proved it: rode the trend then banked +$131 via DAYTRADE_PROFIT_RATCHET @15:31 (exit 30608.5 = its trigger); net +$303 today. The whole "ratchet not firing" scare = the display artifact + point-in-time snapshot misreads (the deepening trough makes a stale-peak-vs-later-price comparison look like a missed fire; and a fresh re-entry's P&L looks like the old position giving back). ALWAYS verify ratchet "misfires" against the trades table exit_reason, not live snapshots.

**Bug B — re-attach records wrong entry (branch `fix/futures-short-stop-reattach`, HEAD c6b9817b).** At reopen the orphan re-attach (`attach_futures_trail`) registered the stop with `entry_price = initial_trigger_price`, so a short's stop recorded entry on the LOSS side (entry==stop, MES 7580.25 vs real avg_cost 7555.25). That corrupts the runner's **profit-ratchet exit + time-stop**, which anchor on `entry_price` (`futures_stop_logic.py:363/375`) — the mechanism that actually banks a native-trail short's profit. Fix threads true ledger `avg_cost` through `attach_futures_trail`→`AttachFuturesTrailRequest.entry_price`→`register_bracket_stop` (`routes_stops.py:219`); optional on the wire, trigger-fallback for legacy. New `_ledger_avg_cost()` mirrors the adapter's `_db_entry` lookup. 4 tests.

**NOT a bug (corrected the trace's overstatement):** the futures runner deliberately does NOT trail the stop when `native_trail_pct` is set (`futures_stop_logic.py:357-362`) — the native trail owns the stop as a wide loss-cap; profit is banked by the runner-side profit-ratchet EXIT, not by trailing. So `modify_count=0` is BY DESIGN; `daytrade_stops.py` long-only + `stops.py` ratchet-up-only are the equity path, not futures. Did NOT change trailing semantics.
