Recurring on the maintenance sweeps: the `orders` DB table accumulates many rows stuck at `status='SUBMITTED'` (10+ across a session of trading) that feed the `R4_ORDER_STUCK_SUBMITTED` WARN alarms.

**Root cause (confirmed 2026-06-16):** these are FILLED orders whose status never synced from the broker to the DB. The broker's `/orders` correctly reports them **FILLED** (its in-memory registry is right); the persisted `orders` table row stays `SUBMITTED`. So it's a broker→DB order-status persist gap on futures bracket entries/exits, NOT vanished orders.

**The broker NAMES it itself** — the reconcile loop logs every ~60s: `Y-RECONCILE.2: N SUBMITTED order(s) have a fill but never transitioned off SUBMITTED — NOT drift-cancelling (would erase a real fill)... the OrderFilledV3 emission gap; recover via fill replay.` So root cause = **the OrderFilledV3 event isn't emitted on fill**, and the recovery is a **fill replay** (ops/code, flag-and-wait — NOT a sweep action). The broker handles it SAFELY (refuses to drift-cancel real fills).

**Same gap also leaves stale `stops` rows.** When a bracket's stop child fills/cancels at IBKR but OrderFilledV3 doesn't emit, the `stops` table row stays **ACTIVE on a now-flat book** — looks like an orphan stop (Domain-B Phase 1 / §253 escalation criterion) but is NOT a live orphan: broker `/orders` working set = NONE (verified). Before escalating an ACTIVE-stop-on-flat, ALWAYS confirm the broker has zero working orders → if so it's this gap, benign. **Reboot behaviour (confirmed 2026-06-16, broker restart 21:07 UTC):** startup force_resync clears the stale ACTIVE **stops** (stops table reset from IBKR truth) ✓ — but the stuck **SUBMITTED orders SURVIVE the reboot** (the `orders` table is NOT force-resynced; it reloads from DB still-SUBMITTED, and the Y-RECONCILE.2 logic re-detects "filled-but-stuck" and again refuses to drift-cancel). So the orders-table staleness only clears via the actual **fill replay** (ops/code, flag-and-wait). It is COSMETIC: the broker's in-memory registry knows they're FILLED, so the order-cap gate does NOT count them and they do NOT block new entries (verified the count stays well under the per-symbol cap). Not a sweep action; flag for the operator if it grows toward a per-symbol cap.

**Do NOT ghost-sweep them.** The maintenance ghost-sweep playbook is for DB=SUBMITTED that the broker **404s** (vanished). These are the opposite — broker=FILLED. Marking a filled exit "terminal/swept" would misrepresent a real fill. Before any sweep, ALWAYS check the broker's status for the coid: FILLED ⇒ leave it (sync lag), 404 ⇒ true ghost (sweepable per the exit-side/age>1h rules).
