2026-07-17 INCIDENT + FIX (V7 core safety). A live LONG 1 MNQ opened 23:41 @ 29120.75 sat NAKED (no stop at IBKR) and bled ~−$400 over 3h before the operator flattened it manually (via `python -m gazbot7.eod_flatten`, which showed `Error 10147 OrderId not found` = no stop order existed at the venue).

**Root cause (confirmed, not guessed):** `core.venue_audit_loop` SILENTLY `continue`d every cycle for 3h — proven by ZERO auditor pages (no naked/reprotect/flatten/drift/exit-stuck) AND max_hold_minutes=120 never firing either (both live behind the same skipped snapshot code). Mechanism: `reqCurrentTime` kept answering, so `gw.healthy`, `probe_alive`, and `liveness_loop` all stayed GREEN and the heartbeat reported healthy — while `reqPositions`/`reqAllOpenOrders` failed, so `_read_venue_protection` hit its `except: return None` and the loop skipped. "Can't check" read as "all clear." The stop itself was likely never live (broker_adapter.place_stop fires placeOrder + returns the coid WITHOUT confirming it landed; `is_naked`/`safe_flatten_verdict` are well-designed but the auditor that runs them was dead). ⚠️ My first story ("23:45 gateway restart orphaned the stop") was WRONG — the gateway never restarted (NRestarts=0, up since 21:05) and the MD quote stream never gapped; operator correctly pushed back. Verify before asserting a root cause.

**Fixes (commits 06349af core + ba84f0d repricer, pushed, tests pass, DEPLOYED — core+shadow restarted while flat):**
1. **Protection-unverifiable watchdog** (core.py): a HELD position that can't be verified escalates instead of silent-skip — `_on_unverified_protection` pages fast (UNVERIFIED_PAGE_CYCLES~15s) then `gw.force_reconnect()` (new public method) to heal the reqPositions path (~30s), re-paging every ~5min. Flat desk stays silent.
2. **Protection surfaced to the sweep**: core writes a `protection` block (held/verified/verified_age_s/unverified_cycles) to core_health.json + status.json; sweep `check_position` now CRITs on held-but-unverified instead of always reading "OK" on core/store agreement (agreement ≠ protection — the exact blind spot).
3. **−€58k shadow poison** (repricer.py, SEPARATE bug found same night): IBKR no-quote SENTINEL bid=-1.0/ask=-1.0 passed the `IS NOT NULL` filter → a session-close hold repriced on a truncated window scored a +$70 winner as −$58,350 ((−1−29175)·2), frozen forever across 5 rows (1243-1247). Fix: `_quotes_for` requires `bid>0 AND ask>0`; `reprice_pending` DEFERS trades whose window outruns captured clean data (never freeze a partial score); reprice returns no_data on entry/atr ≤0. Purged the 5 rows → re-repriced clean (+17.5/+41.5/+54). Board back to sane (−$715).

A placement that never lands is caught + re-armed in seconds, not only by the 5s poll.

Added TradeTracker.has_applied/forget.

**★ RECURRENCE 2026-07-22 (multi-slot tournament, SAME CLASS, harder failure + FIXED).** This time the whole `MultiSlotCore.venue_audit_loop` DIED — an unhandled exception escaped the coroutine (it had NO try/except), so the task silently stopped. The safety spine it runs (naked-audit, drift-halt, **max-hold**, **stop-breach guard**) all went dark while the MAIN loop kept writing a fresh green heartbeat. A `grind_long` LONG 1 rode **153min past the 120-min max-hold**, its 1-ATR stop toothless (price 87pt past it), closing −$216 vs the ~−$27 the stop should have capped. `sweep.py` read OK the whole time (it trusts the main heartbeat). A coincidental IBKR disconnect (04:34, nightly reset, self-healed 04:36) was a red herring. Resolved by operator-authorised `systemctl restart gazbot7-tournament` → adopted the slot from the durable ledger, revived auditor fired the overdue MAX_HOLD immediately → flat.

**FIX (2026-07-22, DEPLOYED, tests+lint green, desk restarted flat):** (1) `venue_audit_loop` cycle is now exception-**GUARDED** — a throw logs + pages `AUDIT_LOOP_ERROR` (once) + **CONTINUES**, never kills the task. (2) The loop stamps `_last_audit_ok_mono` each non-raising cycle; `write_heartbeat` exposes `audit_age_s`. (3) `sweep.py check_core` CRITs (+ fails preflight) when `audit_age_s > 30` while live — so a dead/hung auditor is VISIBLE, not hidden behind the main heartbeat (`multislot_core.py` AUDIT_STALE_S=30, sweep detail now shows `audit Xs`). (4) **★ AUTO-RESTART (no human, 2026-07-22 later):** the run loop gates the systemd `WATCHDOG=1` ping on `core.audit_stale()` — a stale auditor → **withhold the ping** → systemd (`WatchdogSec=90`, `Restart=on-failure`) restarts the desk in ≤90s → re-adopts open slots from the ledger → the revived loop fires any overdue max-hold. A dead/hung auditor SELF-HEALS in ~2min (the exact restart that fixed the incident, automated), not riding a position all night. `audit_stale()` returns False when `_last_audit_ok_mono is None` (not-started/dry desk) so it can't self-restart at boot; verified no restart-loop (audit_age cycles ~2-5s « 30s → pings normally). The lesson generalised: a safety loop must prove its OWN liveness AND a stalled one must trigger RECOVERY, not just an alarm.

**★ TOOTHLESS-STOP ROOT CAUSE + FIX 2026-07-22 (operator: "are we actually placing them?" — right to push; I'd asserted "IBKR paper quirk, nothing we can do" WITHOUT verifying = wrong).** Root cause found: we placed a plain `StopOrder` (stop-MARKET, `lmtPrice` UNSET). We ARE placing them successfully (they rest `PreSubmitted`/`whyHeld=trigger`, naked auditor sees them) — but IBKR's PAPER account attaches its OWN limit ~1 ATR toward entry (≈ the entry price), on the WRONG side: a SELL stop gets a limit ABOVE the trigger → on trigger it tries to sell above the market → NEVER fills. Confirmed on live stops (stp-000003 trig 29131.5/lmt 29143; id114 trig 29310.25/lmt 29324.25≈entry). That's every STOP_UNFILLED + the −$216 MAX_HOLD. **FIX (`broker_adapter.py`, DEPLOYED, tests+lint green):** place an EXPLICIT stop-LIMIT — `StopLimitOrder(side, qty, lmt, trig)` with `lmt = stop_limit_price(trig, side, tick)` = `STOP_LIMIT_BAND_PTS`=20pt PAST the trigger on the FILLABLE side (SELL→below, BUY→above, rounded loosening). IBKR uses OUR limit → fills on trigger (bounded slippage) instead of its toothless one; strictly better LIVE too (caps a naked market fill). The stop-breach guard still backstops a gap > band. ⚠ CONFIRMATION PENDING: must SEE the next real stop echo `lmtPrice` on the fillable side (below trigger for SELL) — if IBKR still overrides, fall back to a PROACTIVE guard (market-flatten at the level). LESSON (again): verify a root cause before asserting; "nothing we can do" needs proof.
