I. Executive overview

GAZBOT is a continuously-running quantitative research machine that happens to also trade. Its defining property is not that it places orders — thousands of products do that — but that it accumulates research: every market observation, every simulated decision, every experiment result and every refuted idea is written to a queryable historical store and remains available to all future research, indefinitely.

Repositioned as a research agent rather than an execution bot, the product is best described as: an always-on instrument that watches a market, forms and tests hypotheses about it, records the verdicts permanently, and produces a weekly scientific report on what it learned.

II. What GAZBOT does, end to end

MARKET → CAPTURE → STORE → OBSERVE → HYPOTHESISE → SIMULATE → SCORE → REPORT → DECIDE │ │ │ │ │ │ │ │ │ │ tick/quote 3-tier continuous research parallel independent weekly promote / │ /bar/L2 storage monitoring candidate shadow re-pricing dossier park / │ feeds tiers of the generation execution on real refute │ live tape tick data
  1. Capture. Broker market data is consumed continuously and written to local storage — trade ticks, quotes, aggregated bars, top-of-book and full 10-level depth snapshots at sub-second cadence.
  2. Store. Data lands in a hot transactional tier, is mirrored nightly to a columnar analytical lake, and is replicated off-site. Each tier has a different lifetime and a different job.
  3. Observe. A live decision layer reads the tape continuously and maintains a structured, machine-readable view of market state.
  4. Hypothesise. Candidate research ideas are generated from observed structure, from failure analysis of prior decisions, and from the weekly report's own findings.
  5. Simulate. Candidates run as shadow arms — full decision logic executing against the live tape in parallel with the real desk, placing no orders. Dozens run concurrently.
  6. Score. Every simulated decision is independently re-priced against captured tick data, producing an honest fill-aware result rather than an optimistic bar-price approximation.
  7. Report. A 21-phase weekly pipeline analyses the accumulated record and produces a structured research dossier with findings, verdicts and proposed next experiments.
  8. Decide. Findings are promoted, parked or refuted — and the verdict itself is stored, so the same ground is never re-litigated from scratch.

III. What problem it solves

The central problem in systematic trading research is not generating ideas. It is that research evaporates. A typical practitioner:

  • runs a backtest in a notebook, gets a number, and loses the notebook;
  • cannot reconstruct what data, code version or assumptions produced last month's result;
  • re-tests ideas that were already refuted, because the refutation was a conversation and not a record;
  • has no measurement of what a rejected idea would have done since rejection;
  • discovers too late that a promising backtest was an artefact of a data or methodology defect.
GAZBOT's answer is to treat research as durable infrastructure rather than as activity. Ideas become registered, numbered, permanently-identified experiments. Results become rows. Verdicts become records with the evidence attached. A refuted idea keeps running in simulation so the refutation stays live rather than becoming folklore.

How components communicate

  • Internal message bus. The market-data service publishes normalised messages on a local topic-based stream. Consumers subscribe by topic. The bus is multi-instrument, and every consumer is required to filter by instrument — a rule enforced because violating it once corrupted every downstream volatility calculation.
  • Shared files as contracts. Cross-process state uses atomically-replaced JSON documents (health, position, switch state, open-simulation snapshots). This makes state inspectable by any process, any script, and any human, without a service dependency.
  • Databases as the integration point. Research and analytics components integrate through the stores rather than through APIs, which means any new tool can read the entire research history with no coordination.
  • Process isolation by design. Each desk holds its own broker session identity. A fault in one cannot cancel another's orders — this is enforced in code and verified by the reconciliation layer.

VI. Data architecture

The three-tier model

History lives in three places with deliberately different lifetimes. This is the single most commercially reusable piece of the system.

TierTechnologyLifetimePurpose
HotSQLite (WAL)A few trading daysWhat the live desk reads. Low latency, transactional, small working set.
LakeParquet, zstd-compressedNever prunedThe permanent analytical record. Columnar, partitioned, cheap to scan.
ArchiveParquet, frozenPermanentPrior-generation capture, retained and still queryable.
Off-siteObject storage (4 buckets)PermanentDisaster recovery; encrypted for state, plaintext columnar for tape so it is queryable in place.

Parquet, exactly how it is used

  • Partitioning: one file per stream / instrument / day. Currently 163 partitions, 702 MB. A query for one instrument-day touches exactly one file.
  • Written by a nightly mirror job that exports completed days out of the hot store using the analytical engine's native COPY … (FORMAT parquet, COMPRESSION zstd). No heavyweight dependency is required.
  • Verified before it counts. The mirror re-reads each written file and compares row counts against the source. A partition is only recorded as exported once that check passes.
  • Interlocked with retention. The prune job is forbidden from deleting any day the mirror has not both exported and row-count verified. Data cannot be lost by a race between the two jobs.
  • Queryable in place, locally or directly from object storage, with no import step.

Analytical engine (DuckDB)

  • Used as an embedded OLAP layer — no server, no cluster, no separate infrastructure.
  • Attaches the hot SQLite stores read-only and reads Parquet natively, so a single query can span the live tape and years of archive in one statement.
  • A dedicated module presents all tiers as one logical connection, resolving overlaps by day boundary rather than blind union, and explicitly reporting coverage gaps so a study cannot silently assume contiguity across a seam.
  • Handles the analytical workload: aggregations over tens of millions of rows, window functions, re-sampling, joins across tiers.

SQLite — still used, deliberately

  • Hot capture (ticks, quotes, bars, book) — high-frequency append workload.
  • Trade store — the P&L record of truth, with executions, orders and reconciliation state.
  • Research stores — one per instrument, holding simulated decisions and their independently-scored results.
  • Chosen because it is transactional, zero-administration, single-file, trivially backed up, and directly attachable by the analytical engine. The combination of SQLite for writes and DuckDB for analytics is the core of the storage design.

Retention policy

  • Hot tier: a small rolling window of trading days — bounded so the live desk's working set stays fast.
  • Lake: never pruned. This is the permanent record.
  • Research stores: never pruned. A simulated decision from any date remains queryable.
  • Off-site: continuous; state hourly, tape nightly.
  • Retention is enforced by an interlock, not by a cron ordering assumption — see the mirror/prune interlock above.

VII. Research engine

How hypotheses are generated

Four distinct sources, all of which end in the same registry:

  1. Structural observation — recurring behaviour identified in the captured tape by exploratory analysis over the lake.
  2. Failure analysis — decisions that lost, and decisions that nearly worked, are examined for the specific mechanism that failed. Each mechanism becomes a candidate variant.
  3. Report findings — the weekly pipeline explicitly outputs a proposed slate of next experiments with the evidence attached.
  4. Parameter geography — sweeps that map how a result behaves across a parameter surface, used to distinguish a genuine plateau from a fitted spike.

How experiments are defined

An experiment is a declarative record specifying its decision family, its parameters, its exit policy, its instrument, and any regime constraints. Adding one is a single declaration; the harness supplies execution, scoring, storage and presentation. Crucially:

  • Every experiment receives a permanent numeric identifier from a registry, allocated once and never reissued — a retired experiment keeps its number forever. This is what makes "how is experiment 23 doing?" a well-formed question across months.
  • Constraints must be declared, not assumed. Cooldowns, time caps and regime floors are enforced centrally by the harness so that a new experiment cannot silently omit the constraint its research ran under.
This last point is hard-won. Two separate incidents occurred where an experiment shipped without a constraint its own research had used — producing forward numbers that could not be compared to the study that justified it. The harness now enforces declared constraints centrally, and tests pin them.

How experiments are run

Candidates execute as shadow arms: the full decision path, fed the live tape, in parallel with the production desk, placing no orders. Dozens run concurrently at negligible cost. Because they consume the same data through the same code path as the live desk, a shadow result and a live result are comparable in a way that a separate backtester's output is not.

How results are stored and reproduced

  • Each simulated decision is a row: instrument, direction, entry, exit, reason, timestamps, the volatility state at entry, and the exit parameters needed to replay it.
  • A separate table holds the independently re-priced result and its fill status. The two are kept apart deliberately so an optimistic figure can never be mistaken for the honest one.
  • Reproduction is possible because the stored row carries the parameters required to replay the exit against the captured tick data — the re-pricing engine does exactly this, and can be re-run at any time.
  • Configuration changes to live behaviour are journalled, and live-behaviour files are version-controlled with an automated check that they are both committed and pushed off-machine.

How hypotheses are compared

Classification precedes ranking. The system requires every arm to be classified — control, A/B half, factorial cell, or slow-firing — before any performance comparison. This exists because a naive profit-sort once placed a deliberate control arm at the top of a kill list. That control is the only evidence that the live configuration is worth having; deleting it would have destroyed the baseline while appearing to be housekeeping.
  • Paired design. Variants are armed in matched pairs differing in exactly one property, so an effect can be attributed to that property rather than to the cell it happened to occupy.
  • Controls are expected to lose and are protected from retirement on that basis.
  • Judgement is on expectancy and robustness, not win rate.

VIII. Backtesting and walk-forward

Architecture

Two complementary engines:

  1. Forward simulation (the shadow desks) — the primary method. Out-of-sample by construction, because the data has not happened yet.
  2. Historical replay — a race engine that replays a candidate against captured tick data, deciding for each position whether the stop or the target was reached first, in order, at tick resolution.

Inputs and outputs

InputsOutputs
Captured ticks, quotes, bars and depth from the lake; a candidate definition; explicit position, cooldown and hold constraintsPer-decision records with entry, exit, reason, hold time, favourable and adverse excursion; aggregate expectancy, hit rate, profit factor; robustness cuts

Validation methodology and overfitting controls

The system's stated methodological position is that a backtest result is a hypothesis, not a finding. The following are implemented rather than aspirational:
  • Tick-resolution race, never bar approximation. The engine determines whether the stop or the target came first at tick level. A method that counts how often price reached a target while ignoring whether the stop came first was found to inflate an apparent hit rate dramatically and to have shipped a losing configuration; that method is banned.
  • Two independent scoring paths. An optimistic bar-price figure and an honest tick-re-priced figure are computed separately. On one identical population the two disagreed in sign for half the arms. Only the honest one may be used for judgement.
  • Leave-one-out robustness. Results are recomputed with the best day removed, and with the best three removed. A result carried by one session is visible immediately.
  • Both-halves test. A result must hold in both halves of its window, not only in aggregate.
  • Placebo arms. Candidates are run against randomised or sign-flipped variants; a signal that also "works" on the placebo is rejected.
  • Parameter-surface inspection. Neighbouring parameter cells must also be positive. An isolated peak is treated as a fit, not an edge.
  • Look-ahead auditing. Time-alignment defects are actively hunted — three separate look-ahead bugs were found inside the system's own research harnesses, each of which would have manufactured an edge that did not exist. Detection of these is now part of the weekly process.
  • Cost re-derivation. Transaction cost is re-derived from mechanism rather than copied from a report, after an incorrect cost constant was used to kill a viable candidate.

Out-of-sample and feedback

Forward shadow running is the out-of-sample test, and it is continuous rather than a one-off holdout. A candidate that survives historical validation is armed in shadow and accumulates genuine unseen data from that moment. Promotion requires a stated forward threshold — a minimum expectancy over a minimum number of forward decisions, explicitly including a regime the candidate was not fitted on. Results feed back into the registry, into the weekly report, and into the next round of hypotheses.

IX. Near-miss and failure analysis

What is recorded

How near misses become hypotheses

A decision that stopped out but had substantial favourable excursion first is not simply a loss — it is a timing or exit hypothesis. A decision that was suppressed by a filter and would have worked is a filter calibration hypothesis. Because the system records both the suppression and the counterfactual, these become measurable rather than anecdotal, and the weekly report surfaces them as proposed experiments.

How prior research is retained

  • Every lead ends in one of four states: live, shadow, parked, or refuted. "Quietly abandoned" is not permitted. A parked lead retains its revival condition.
  • A refuted idea keeps a shadow arm running where practical, so the refutation is continuously re-tested rather than frozen. A verdict resting on a small sample and no ongoing instrument is treated as an open question, not a closed one.
  • Null results are recorded as first-class findings so they are not re-derived. Several are documented specifically to stop future work repeating them.
  • An append-only session log, an architectural decision record, and a permanent experiment registry together mean the reasoning survives, not just the numbers.

The compounding property. Because every cycle adds rows and never removes them, the research base grows monotonically. A hypothesis proposed in month twelve is tested against twelve months of captured tape and evaluated in the context of every experiment already run. The system's analytical capability therefore increases with age — the opposite of a backtest script, whose value is fixed at the moment it is run and decays as the market moves on.
Stated honestly: the loop's hypothesis-generation stage is currently the least automated. Structure detection, failure analysis and report generation are automated; the judgement that turns an observation into a well-posed candidate is model-assisted and human-supervised. This is the most valuable place to invest for a commercial product, and it is also the place where over-claiming would be easiest.

XI. The weekly research report

Inputs

  • The full live trade record with reconciled executions
  • The complete shadow research book, honestly re-priced
  • The routing decision log and its scored audit ledger
  • The captured tape across all tiers, for fresh analysis
  • Prior reports, so findings can be tracked across weeks

Architecture

A 21-phase pipeline, one operating-system process per phase. Phases cover: live desk performance, the secondary desk, the shadow book, routing analysis, strategy rehabilitation, several independent greenfield research clusters, chart generation, then assembly, proofreading, revision and finalisation.

  • The artefact on disk is the checkpoint. A re-run resumes rather than restarts.
  • One process per phase keeps memory flat on a constrained host.
  • Judged on the artefact, never the exit code — a phase that exits successfully having produced nothing is treated as a failure, because that exact silent failure occurred.
  • Budget-aware scheduling. A preflight compares declared phase timeouts against the real time budget; each phase is capped at a fair share; a phase that would receive a useless sliver is skipped and logged rather than silently truncated. Greenfield research clusters rotate week to week so the full space is covered over time rather than only the phases that happen to run first.
  • The tail is reserved — assembly, proofread, revision and finalisation get a protected allocation. Research can be lost; the write-up cannot.
  • A shared data contract is injected into every phase so no phase can quietly use the wrong data window or the wrong cost assumption.

What the report contains and how it identifies discoveries

Per-strategy performance with robustness cuts; regime segmentation; exit-mix and excursion analysis; the shadow book as the explicit counterfactual for anything that was benched; greenfield research findings with placebo results; a register of instrument failures found in its own harnesses; and a closing section proposing the next slate of experiments with evidence and build cost per item.

A "discovery" is only reported with the sample size, the robustness cuts, and an explicit statement of what would refute it. The pipeline includes an adversarial revision pass whose job is to attack the draft's own conclusions before publication.

Can it operate indefinitely as the database grows?

Structurally yes, with one caveat. The columnar lake is partitioned by day and by instrument, so per-query cost scales with the window examined rather than with total history — a one-week analysis costs the same in year five as in month one. Phases are independent processes with capped memory, so a larger corpus does not raise peak memory.

The caveat is that any phase deliberately scanning all history grows linearly. The mitigation already in place is the fair-share budget with explicit logging of what was skipped; the productised answer is pre-aggregated summary tables per period, which the architecture supports but which is not yet built.

What the model receives and produces

Receives: deterministically-computed context — market state summaries, per-strategy performance, health status, position and reconciliation state, and an explicit rules prompt. It reads prepared facts; it does not roam.

Produces: a structured decision plus a written rationale. The rationale is logged in full, so every automated decision has a durable, human-readable justification attached — a property most automated systems lack entirely.

Deterministic versus generated

The boundary is strict and architectural. Everything that touches money is deterministic code: order placement, position management, stops, flatten logic, reconciliation, safety. The model's entire authority is a permission layer — which strategy families may open new positions — expressed as a single file. Any model error or malformed output results in no change, and the system continues on its previous state, benching-only. It cannot invent a trade.

Could it support other LLMs?

Yes, with modest work. Integration is via a command-line invocation returning structured output, with fail-safe parsing. Swapping providers means replacing that invocation and re-tuning prompts. The prompts themselves are external Markdown files, not embedded strings — deliberately, so they can be edited and versioned without code changes. Nothing depends on provider-specific APIs. For a commercial product this would be abstracted behind a provider interface; the seams are already in the right places.

XIV. Broker and data integration

  • Gateway: a containerised broker gateway holding one authenticated session. Currently Interactive Brokers.
  • Session isolation: each desk connects with its own client identity. Cross-desk interference is structurally prevented and continuously verified.
  • Market data: streaming trades, quotes and aggregated bars, republished on the internal bus.
  • Depth: a separate service records 10-level book snapshots at sub-second cadence per instrument.
  • Historical: broker historical data can be pulled for instruments predating local capture, with request pacing respected and a preflight that refuses to run while the desk holds a position — the research pull must never compete with trading for the session.
  • Account integration: positions, orders and executions are read continuously. Broker state is treated as the sole truth; internal books are treated as intent and are reconciled against executions.

Required from the customer: a brokerage account with market-data entitlements for the instruments studied, credentials for the gateway, and a host meeting the deployment requirements below. Research-only operation needs data entitlements but no trading permissions.

Scalability

  • Instruments: the bus, capture and storage are already multi-instrument, and per-instrument research desks with isolated stores are an established pattern. Adding an instrument is largely configuration. The practical limit is market-data bandwidth and host memory, not architecture.
  • Trades and experiments: negligible. Tens of thousands of research rows are trivial for the analytical layer.
  • Historical data: the columnar lake is the scaling story. At 10× (~7 GB, ~1,600 partitions) nothing changes — partition pruning means query cost tracks the window examined. At 100× (~70 GB) the lake still functions locally, and queries can run directly against object storage; hot-tier retention and off-site sync windows would need attention, and pre-aggregated period summaries become worthwhile.
  • The real constraint is host memory during the weekly report, already mitigated by one-process-per-phase and explicit memory limits.

Current limitations and technical debt

Stated plainly, because a buyer will find these anyway.
  • Absolute paths are hard-coded throughout. Installation-root and data-root abstraction is a prerequisite for distribution.
  • Single-tenant. No user model, no per-customer isolation, no authentication on the dashboard.
  • Instrument specifics appear in code — contract multipliers, cost constants, session clocks. These need to become an instrument registry.
  • Operational knowledge lives in Markdown, not in the software. The system is unusually well documented, but that documentation is currently a human-facing operating manual rather than product behaviour.
  • Session-based model authentication requires periodic interactive login — the single largest obstacle to unattended commercial operation.
  • Retired-generation code remains present alongside live code; a customer distribution needs it removed.
  • Manual installation. No installer, no migrations, no upgrade path.
  • Prompts are tuned to one operator's judgement and encode this desk's history. They generalise poorly without abstraction.
  • Alerting is single-channel and assumes one operator.

XVII. The skeptic's ten

Written in the voice of a professional systematic trader evaluating GAZBOT, based only on what is actually in the codebase — not on what would sound impressive.

I have looked at a lot of retail trading software. Most of it is a strategy with a chart attached. Here is what is genuinely unusual here, and I have deliberately excluded the things that merely sound good.

1. It re-prices its own simulations against tick data, and keeps the optimistic number separately so it cannot be used by accident

Nearly every backtester I have seen fills at the bar. This one replays each simulated position against captured ticks and asks which came first, the stop or the target. It stores the optimistic figure and the honest figure in separate tables. On one identical population of several hundred decisions, the two disagreed in sign for half the strategies. Most products would have shipped the flattering number and never known.

2. Rejected strategies keep running

Everywhere else, a rejected idea is deleted. Here a refuted idea is often left running in simulation so the refutation is continuously re-tested. During review, a strategy benched eighteen days earlier on a sample of eleven decisions was identified as having no ongoing instrument — and the response was to arm a shadow twin so the verdict gets priced continuously. That is a research culture encoded as software, not a feature list.

3. It runs deliberate control arms that are supposed to lose, and protects them from deletion

The single most professional thing in this system. There are control arms carrying five-figure losses whose entire purpose is to be the baseline. The codebase explicitly records an incident where a profit-ranking put the control at the top of a kill list, and the rule that emerged — classify before you rank — is now enforced. I have worked at firms that did not do this.

4. Its self-monitoring is designed against a named failure mode, not against "is the process alive"

The recurring theme is: an instrument that reports healthy about something it never checks. Concrete instances found and fixed include a monitor that verified a job was committed but never that it had left the machine; a research desk that was "active", consuming CPU, and had never once been capable of firing; and staleness alarms measured on wall-clock across a weekend when the market was shut. Each produced a specific check. This is a system that has been embarrassed by reality and learned.

5. Look-ahead bugs are hunted inside its own research harnesses, and found

Three separate time-alignment defects were caught in its own tooling — a five-second look-ahead that manufactured an entire regime-specific edge, a leak that reversed a strong statistical result once removed, and an integer-division error that silently read five-second bars as one-minute bars for hours. Each is documented with what it was worth. Anyone can claim they avoid look-ahead; this is the only retail-scale system I have seen that treats finding them as a standing weekly job.

6. The storage design is genuinely good engineering, not a database with a folder next to it

Hot transactional tier for the live path, permanent columnar lake for analysis, off-site replication, and — the part I would actually steal — an interlock forbidding the prune job from deleting any day the mirror has not exported and row-count verified. That is the difference between "we have backups" and "data loss is structurally impossible". Tens of millions of rows, tick-level history, and no database server or cluster anywhere.

7. The LLM cannot place a trade, and that boundary is architectural rather than a promise

The model's total authority is a permission file naming which strategy families may open positions. Every money-touching path is deterministic. A malformed model response results in no change and the system continues benching-only. Given how many "AI trading bots" hand a language model an order API, having the boundary drawn in exactly the right place — judgement in, execution out — is the most credible design decision here.

8. Every automated decision carries a written rationale, permanently

The routing layer logs a full paragraph of reasoning for every five-minute decision, and there is a scored audit ledger grading past decisions — including the bad ones, with the lesson extracted. I can go back to any afternoon and read why the system did what it did. I cannot do that with any commercial product I have used, and I frequently cannot do it with my own code.

9. Experiments have permanent immutable identifiers

Small, and it changes everything. Numbers are allocated once and never reissued; a retired experiment keeps its number. It means "how is 23 doing?" survives across months. The codebase also records the failure of a dashboard that numbered experiments by array position and drifted until most numbers were wrong — and the fix was to make the display read the registry. That is a team that understands that two surfaces disagreeing is the actual enemy.

10. It knows, and records, the difference between "no setup" and "broken"

This is the one I would pay for. Most systems cannot distinguish a strategy that found no opportunity from a strategy that is silently dead. This one records suppressed signals, whether a strategy wanted to act and was blocked versus could not have acted at all, and now publishes open simulated positions so a blocked strategy is visibly blocked. It found a research desk that had produced nothing for three days while appearing perfectly healthy — and the response was both to fix it and to build the check that would have caught it on day one.

What would still make me hesitate

In fairness, and because a buyer will ask:

  • The forward sample is young. The methodology is excellent; the accumulated evidence is weeks, not years. The machine is more proven than any individual finding it has produced.
  • It is single-tenant and hand-installed. Nothing about the research core prevents productisation, but the wrapper does not exist yet.
  • Unattended operation depends on session-based model credentials that need periodic interactive renewal. That must be solved before anyone sells this.
  • The hypothesis-generation step is the least automated part of the loop — which is precisely the part the marketing will be most tempted to overstate.
Summary judgement. As a trading bot this would be one of many. As a research instrument it is unusual, and the unusual parts are the ones that are hard to copy: honest scoring, controls, permanent research memory, and self-instrumentation built by being wrong and noticing. The product is not the strategies. The product is the machine that evaluates them.
