★★★ WHY YOU ALMOST READ LAST WEEK’S REPORT TONIGHT — and the guard that now stops it

This report was one build away from being the 2026-09-18 edition, re-published under tonight’s date. You are owed the mechanism, because you have been handed a silently stale build before and a promise is not a guard.

What happened. friday_phases._report_week() resolved the report week as “the most recent Friday whose 22:00Z session cut has already passed”. The cron starts at 21:05Z on Friday — 55 minutes before that cut — so on Friday night it always rolled back seven days. Measured at 21:05Z tonight it returned WEEK = 2026-09-18 while the clock said 2026-09-25. Every phase was handed the wrong week, assemble’s output resolved to weekly_2026-09-18.html which already existed, and the runner’s freshness check passed it because a git operation on 09-24 09:43 had touched every fragment, making all four look newer than the 09-18T22:00Z cutoff. The log read sections: 0 built, 4 already had, 0 missing then HAVE assemble — skipping. That is the exact failure the checkpoint’s own docstring says it exists to prevent: “a way to publish last week twice”.

The two fixes, both on disk. One — on a Friday the report week is today, because a Friday-night run is about the week ending tonight. That is the only run instant that changes; a Saturday or Sunday resume already named this Friday, so the fix makes the cron AGREE with its own resume rather than contradict it. Two — an mtime cannot say what week a file is ABOUT, so every artifact now carries a week stamp written by the runner when the phase succeeds, and a stamp that disagrees with the report week is STALE no matter how new the file is. Verified tonight: with mtimes untouched, all four body phases flipped from HAVE to todo on the stamp alone.
